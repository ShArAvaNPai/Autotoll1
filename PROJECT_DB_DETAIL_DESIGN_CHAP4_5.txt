Chapter 4: Database Design (Pages 10-12)

4.1 Introduction
The database layer is critical for maintaining consistency between vehicle registrations, financial transactions, and historical detection logs. AutoToll AI employs a hybrid approach, using Supabase (PostgreSQL) for persistent, cloud-accessible user data and SQLite for high-speed local caching during inference. Additionally, for the AI component, a specific dataset is used to train the vehicle detection model.

4.2 Dataset Overview (Vehicle & License Plate Dataset)
To ensure accurate vehicle detection and classification, a custom dataset was curated. The dataset primarily consists of images captured from CCTV footage at various angles and lighting conditions, simulating real-world toll plaza environments. It includes labeled instances of vehicles and their corresponding license plates.

4.3 Dataset Structure
The dataset is organized into two main directories: `images` and `labels`.
- **Images**: Contains the raw .jpg/.png files.
- **Labels**: Contains accompanying text files with bounding box coordinates.
The directory structure follows the standard YOLO format:
dataset/
├── train/
│   ├── images/
│   └── labels/
├── valid/
│   ├── images/
│   └── labels/
└── test/
    ├── images/
    └── labels/

4.4 Annotation Format (YOLO V8 Format)
The annotations are stored in `.txt` files where each line represents a detected object.
Format: `<class_id> <x_center> <y_center> <width> <height>`
- `class_id`: Integer representing the object class (e.g., 0 for Car).
- `x_center`, `y_center`: Normalized coordinates of the center of the bounding box (0-1).
- `width`, `height`: Normalized dimensions of the bounding box relative to the image size.

4.5 Number of Records
- **Total Images**: ~5,000 labeled images.
- **Training Set**: 3,500 images (70%)
- **Validation Set**: 1,000 images (20%)
- **Test Set**: 500 images (10%)
This distribution prevents overfitting while ensuring the model generalizes well to new data.

4.6 Data Classes (Vehicle Types)
The model is trained to recognize specific classes relevant to toll calculation:
1. `Car`: Standard passenger vehicles.
2. `LCV` (Light Commercial Vehicle): Small trucks and vans.
3. `Bus/Truck`: Heavy transport vehicles.
4. `Motorcycle`: Two-wheelers (often toll-exempt but tracked).
5. `License Plate`: The specific region containing the registration number.

4.7 Data Splitting
The dataset is split randomly but stratified to ensure a balanced representation of all classes in both training and validation sets. This is crucial to prevent the model from becoming biased toward the most common vehicle type (typically cars).

4.8 Justification for Dataset Choice
The chosen dataset includes diverse scenarios such as night-time traffic, rainy conditions, and varied camera angles. This variety is essential for training a robust model capable of performing reliably in an uncontrolled outdoor environment, which is the primary operational setting for AutoToll AI.

4.9 Conclusion
A well-structured dataset is the foundation of high-performance AI. By adhering to standard YOLO formats and ensuring a balanced class distribution, the database design supports both the backend logic (via PostgreSQL) and the frontend AI intelligence (via the trained model).

Chapter 5: Detail Design (Pages 13-15)

5.1 Introduction
This chapter delves into the internal logic and interaction flows of the system's core modules. It explains "how" the requirements are implemented, detailing the algorithms and state management strategies used.

5.2 System Overview
The system operates as an event-driven loop:
1. Video Frame Acquisition -> 2. AI Inference -> 3. Data Extraction -> 4. API Request -> 5. Database Transaction -> 6. UI Update.

5.3 Module-wise Detailed Design

    5.3.1 Live Monitoring & Detection Module
    - **Trigger**: New frame available from camera stream.
    - **Logic**: The frame is passed to the YOLOv8 engine. If a "Vehicle" class detection exceeds 50% confidence, the "License Plate" sub-region is cropped.
    - **State**: Maintains various states like `IDLE`, `DETECTING`, `PROCESSING`, and `COMPLETED` to manage UI feedback.

    5.3.2 Vehicle Registry & Owner Portal
    - **Function**: Manages user authentication and profile data.
    - **Flow**:
      - User logs in with `License Plate`.
      - System fetches `Owner` record joined with `Vehicle` table.
      - Displays `Wallet Balance` and `Transaction History`.
    - **Security**: Uses Row Level Security (RLS) in Supabase to ensure users can only view their own data.

    5.3.3 Funds & Wallet Management Module
    - **Logic**:
      - `check_balance(vehicle_id)`: verifying funds.
      - `deduct_toll(vehicle_id, amount)`: atomic transaction update.
      - If `balance < amount`: Return `INSUFFICIENT_FUNDS` error code.
    - **Design**: Implements a credit-based system where money is deducted from a pre-paid wallet rather than real-time bank transactions, maximizing throughput (speed).

    5.3.4 ALPR Processing (YOLO + OCR Pipeline)
    - **Pipeline**:
      1. Crop Plate Image.
      2. Convert to Grayscale & Apply Thresholding (OpenCV).
      3. Pass processed image to EasyOCR `readtext()`.
      4. Filter results using RegEx `^[A-Z]{2}[0-9]{2}[A-Z]{1,2}[0-9]{4}$` to validate Indian license plate formats.
    - **Fallback**: If OCR confidence is low (<0.4), flag as `REVIEW_NEEDED`.

    5.3.5 Reports & Analytics Module
    - **Logic**: Runs SQL aggregation queries (`COUNT`, `SUM`, `AVG`) on the `detections` table grouped by `date` or `vehicle_type`.
    - **Optimization**: Queries are cached for 5 minutes to reduce database load on the dashboard.

5.5 Conclusion
The detailed design ensures modularity and separation of concerns. The AI processing is decoupled from the business logic, allowing for independent scaling. The strict validation in the ALPR pipeline minimizes false positives, directly addressing the key functional requirement of accuracy.
